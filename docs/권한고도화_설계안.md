# 권한 고도화 설계안 (착수 전 컨펌용)

작성일: 2026-10-31 · 상태: **컨펌 완료(추천 기본값 전부 승인) → A·B·C 단계 구현 완료, 배포 전**

## 1. 목표와 현재 상태

| 구분 | 현재 | 목표 |
|---|---|---|
| 계정 | 관리자 1개(.env), 비밀번호 평문 비교 | 여러 사용자, 비밀번호 해시 저장, 관리자가 발급 |
| 권한 | 로그인하면 모든 화면·기능 사용 | **역할별로 화면과 기능을 제한** (예: 발주 화면은 발주 권한자만) |
| 검사 위치 | 없음 | **서버가 모든 API에서 검사**(진짜 방어선), 화면은 메뉴·버튼을 숨김 |
| 기록 | 없음 | 로그인·발주·내보내기·권한 변경 등 감사 로그 |

핵심 원칙: 화면에서 메뉴를 숨기는 것만으로는 막을 수 없으므로(주소를 직접 호출할 수 있음), **서버의 모든 API가 권한을 검사**합니다.

## 4. 기존 화면에 적용되는 변경

**메뉴**: 권한이 없는 화면은 사이드바에서 숨깁니다. 직접 접근하면 "접근 권한이 없습니다" 화면(403)을 보여줍니다.

**버튼 단위**: 화면은 볼 수 있어도 기능은 제한합니다.

| 화면 | 버튼·기능 | 필요한 권한 |
|---|---|---|
| 발주관리 | "+ 발주 등록" | `orders.create` |
| | 상태 변경 선택 | `orders.update` (없으면 상태가 글자로만 표시) |
| 모든 화면 | 내보내기 CSV/엑셀 | 해당 `*.export` |
| 대시보드 위험 알림 | "새로 분석" | `risks.refresh` |
| 데이터 관리 | "데이터 새로고침" | `data.refresh` |

**대시보드 위젯**: 대시보드 하나에 여러 영역의 정보가 섞여 있어, 위젯마다 해당 데이터 권한이 있을 때만 보여줍니다. 그렇지 않으면 발주·재고 정보가 대시보드로 새어 나갑니다.

| 위젯 | 필요한 권한 |
|---|---|
| 2026 예측 수요 KPI, 수요예측 추이 | `forecast.view` |
| 발주 이행률 KPI | `orders.view` |
| 재고 현황·예상 소진일 KPI, 재고 주의 자재 표 | `inventory.view` |
| AI 위험 알림 | `risks.view` |

## 5. 추가되는 화면 4개 + 안내 화면

| 화면 | 필요한 권한 | 내용 |
|---|---|---|
| **사용자 관리** | `users.manage` | 사용자 목록, 계정 발급(아이디·이름·역할·임시 비밀번호), 역할 변경, 비활성화, 비밀번호 초기화, 잠금 해제 |
| **역할·권한 관리** | `roles.manage` | 역할 목록, 권한 체크 매트릭스로 수정, 새 역할 생성. 기본 역할 삭제 불가, 관리자 역할은 권한 축소 불가 |
| **감사 로그** | `audit.view` | 일시·사용자·행위·대상·IP, 기간·사용자·행위 필터, CSV 내보내기 |
| **내 계정** | 로그인한 모든 사용자 | 내 역할·권한 목록 확인, 비밀번호 변경, 최근 로그인 이력 |
| 접근 거부(403) | - | 권한 없는 화면에 직접 접근하거나 권한이 바뀐 경우 안내 |

사이드바에는 "관리" 구분 아래 사용자 관리, 역할·권한, 감사 로그가 `users.manage` / `roles.manage` / `audit.view` 보유자에게만 나타납니다.

## 6. 서버(API) 권한 적용

모든 API에 필요한 권한을 지정합니다. 권한이 없으면 403, 로그인하지 않았으면 401입니다.

| API | 필요한 권한 |
|---|---|
| `GET /api/materials`, `/api/me` | 로그인만 (공통 참조 정보) |
| `GET /api/dashboard` | `dashboard.view` + 위젯별 데이터 권한만 응답에 포함 |
| `GET /api/forecast`, `/series`, `/models` | `forecast.view` |
| `GET /api/orders` | `orders.view` |
| `POST /api/orders` | `orders.create` |
| `PATCH /api/orders/{po}` | `orders.update` |
| `GET /api/inventory` | `inventory.view` |
| `GET/POST /api/simulation*` | `simulation.run` |
| `GET /api/risks` | `risks.view` (`refresh=true`는 `risks.refresh`) |
| `GET /api/export/{orders,inventory,forecast,risks}`, `POST /api/export/simulation` | 각 `*.export` |
| `GET /api/data/status` / `POST /api/data/refresh` | `data.view` / `data.refresh` |
| `GET /api/settings` | `settings.view` |
| 신규 `/api/admin/users*` | `users.manage` |
| 신규 `/api/admin/roles*` | `roles.manage` |
| 신규 `/api/admin/audit` | `audit.view` |
| 신규 `/api/account/*` (비밀번호 변경 등) | 로그인만 (본인 계정) |

## 7. 로그인·계정 보안 강화

| 항목 | 내용 |
|---|---|
| 비밀번호 저장 | 해시(scrypt, 파이썬 표준 라이브러리라 패키지 추가 없음) |
| 최초 로그인 | 관리자가 발급한 임시 비밀번호는 **첫 로그인에서 변경 강제** |
| 비밀번호 정책 | 최소 10자, 영문과 숫자 포함 (조정 가능) |
| 로그인 잠금 | 5회 연속 실패 시 15분 잠금 (관리자가 즉시 해제 가능) |
| 토큰 | 12시간 유지, 사용자별 **토큰 버전**으로 로그아웃·비밀번호 변경·비활성화 시 즉시 무효화 |
| 권한 반영 | 요청마다 사용자·역할을 확인(30초 캐시), 권한을 바꾸면 곧바로 적용 |
| 비상 관리자 | 기존 `.env`의 관리자 계정을 **비상용으로 유지**(DB 장애 시에도 로그인 가능). 사용은 감사 로그에 표시, 환경설정으로 끌 수 있음 |

## 8. 데이터 구조 (Supabase에 새 테이블 3개)

제가 SQL 파일을 만들어 드리면 SQL Editor에서 한 번 실행하시면 됩니다(RLS 켜고 공개 정책 없음).

| 테이블 | 주요 컬럼 |
|---|---|
| `app_roles` | id, name(고유), description, permissions(권한 코드 배열), is_system, created_at |
| `app_users` | id, username(고유), display_name, password_hash, role_id, is_active, must_change_password, failed_logins, locked_until, token_version, last_login_at, created_at |
| `audit_logs` | id, at, username, action, target, detail(JSON), ip |

기본 역할 5개와 첫 관리자 계정은 시드 SQL로 넣고, 첫 관리자 비밀번호는 기존 `APP_ADMIN_PASSWORD`를 해시해 사용하거나 지정하신 값으로 만듭니다.

**감사 로그 기록 대상**: 로그인 성공·실패·잠금, 로그아웃, 비밀번호 변경·초기화, 발주 등록·상태 변경, 내보내기(대상·형식·조건), 위험 "새로 분석", 데이터 새로고침, 사용자·역할 생성·수정·비활성화, 권한 변경.

## 9. 진행 단계 (제안)

| 단계 | 범위 | 규모 | 결과 |
|---|---|---|---|
| **A. 권한 기반** | 새 테이블·시드, 로그인 전환, 서버 전 API 권한 검사, 메뉴·버튼·위젯 숨김, 403 화면, 내 계정(비밀번호 변경) | 대 | 역할별로 실제로 접근이 제한됨 |
| **B. 관리 화면** | 사용자 관리, 역할·권한 관리 | 중 | 코드 수정 없이 계정·권한 운영 |
| **C. 감사·보안** | 감사 로그 기록·화면, 로그인 잠금, 비밀번호 정책 | 중 | 추적·보안 강화 |

각 단계마다 검증한 뒤 배포하고 멈출 수 있습니다. 한 번에 끝까지 진행하는 것도 가능합니다.

**검증 방식**: 역할 5개 × 전체 API 조합을 자동 테스트(허용 200 / 차단 403 / 비로그인 401)로 확인하고, 역할별로 로그인해 화면을 직접 점검합니다.

## 10. 배포 영향과 위험

| 항목 | 내용 | 대응 |
|---|---|---|
| 서버 상태 | 비용 때문에 서버를 중지해 두셨다면 배포 전에 켜야 함. IP가 바뀌었으면 Route 53 레코드 갱신, SSH 보안그룹 규칙 필요 | 배포 시점에 같이 점검 |
| SQL 1회 실행 | 새 테이블 3개와 시드 | 제가 SQL 파일 제공, 실행은 직접 |
| 재로그인 | 토큰 형식이 바뀌어 모든 사용자가 다시 로그인 | 배포 전 안내 |
| 관리자 잠김 | 설정 실수로 아무도 로그인할 수 없는 상황 | `.env` 비상 관리자 유지, 서버 백업 후 배포 |
| DB 의존성 | 사용자·권한이 Supabase에 있어 장애 시 일반 로그인 불가 | 비상 관리자로 로그인 가능, 권한 캐시 |
| 대시보드 정보 노출 | 위젯 단위로 걸러야 발주·재고 정보가 새지 않음 | 위젯별 서버 필터 + 테스트 |

## 11. 컨펌이 필요한 항목 (추천 기본값 포함)

| 번호 | 질문 | 추천 |
|---|---|---|
| 1 | 기본 역할 5개(관리자·구매담당·재고담당·수요계획·조회자)와 3번 표의 권한 구성 | 이대로 |
| 2 | 조회자가 **발주 화면을 못 보는 것**이 맞는지 (요청하신 예시와 동일하게 설계) | 이대로 |
| 3 | 재고담당이 발주를 **조회만** 허용 | 이대로 |
| 4 | 위험 "새로 분석"(AI 호출 비용)을 관리자·수요계획만 허용 | 이대로 |
| 5 | **자재별 범위 권한**(예: 변전기자재 담당은 해당 자재만)이 필요한지 | 이번에는 제외, 필요하면 다음 단계 |
| 6 | 관리자가 **새 역할을 직접 만들고** 권한을 체크하는 기능 | 포함 |
| 7 | 계정은 관리자 발급만(직접 가입 없음), 최초 로그인 시 비밀번호 변경 강제 | 이대로 |
| 8 | 비밀번호 정책(10자 이상, 영문+숫자), 5회 실패 시 15분 잠금 | 이대로 |
| 9 | `.env` 비상 관리자 계정 유지 | 유지 |
| 10 | 진행 방식: A→B→C 단계별 배포 vs 끝까지 진행 후 한 번에 배포 | 단계별(A 후 점검) |
| 11 | 2단계 인증(MFA)은 이번 범위에서 제외 | 제외 |
| 12 | 감사 로그 보관 기간 | 기본은 삭제 없이 보관, 이후 정책 확정 |
